# APEX PC 优先实施方案与进度

更新：2026-09-06。选定方向为珊瑚红。当前交付为开发中的可运行版本，以下明确区分已经实现与尚待完成。

## 视觉与布局

- PC 首页采用左导航、中间照护内容、右侧日历的三栏结构。资料核对采用原文与事项双栏。
- 680px 以下使用四项底部导航；核对页按原件、提取事项顺序排列；960px 以下侧栏内容转为纵向。
- 主色 `#CF4E57`，页面底色 `#FCFAF9`，淡珊瑚背景 `#FFF0EE`，正文暖灰。主操作保持统一，状态同时显示文字，避免仅凭颜色传达信息。
- PC 首页、核对页设计图位于 `designs/desktop`。独立生成的盆栽、清单、心形照护插画位于 `../app/frontend/public/art`，已用于真实页面。生成图片内的虚构姓名和日程不会自动进入业务档案。

## 当前结构

```text
React + TypeScript + Vite（同源 Web）
             ↓ HTTPS /api
FastAPI：账户、资料、核对、照护、问答、机构测算
             ├─ SQLAlchemy → SQLite（本地）/ Supabase PostgreSQL（云端）
             ├─ 原 Python ROI / 知识检索内核
             └─ 持久化任务表 → 后台 worker
                                 ├─ 文本 PDF / DOCX 本地解析
                                 ├─ 百度托管 PaddleOCR-VL API
                                 └─ LangGraph + Kimi K3 境内 API
```

本地原件保存于服务端私有目录；云端适配器使用私有 Supabase Storage bucket，路径按账户和资料 ID 隔离，所有上传、下载、删除均经过 FastAPI 的账户校验。服务端密钥不进入浏览器。数据库迁移启用 RLS 并撤销 anon/authenticated 对业务表的权限，当前由受信任的服务端连接负责授权。

## 数据与接口契约

主要实体：User、LoginSession、Document、Job、Fact、Task、Message、Audit、Simulation。各业务记录具有 user_id；所有读取和变更在服务端校验所有者，机构入口另检查 institution_access。

| 接口 | 契约 |
|---|---|
| POST /api/documents | multipart 单文件；10MB；SHA256 在账户内去重；返回 id、duplicate |
| GET /api/workspace | 当前账户文档、事实、任务；刷新重新读取，不依赖浏览器会话存储档案 |
| GET /api/documents/{id} | 分页文字、来源位置和解析方式 |
| GET /api/documents/{id}/file | 授权原件下载；受限图片/PDF支持 inline 预览 |
| POST /api/documents/{id}/retry | 仅失败作业可重新排队 |
| PATCH /api/facts/{id} | status、version、note；版本不符409；潜在冲突确认必须说明 |
| PATCH /api/tasks/{id} | status、version；无效来源或旧版本409 |
| POST /api/messages | question；引用必须来自本次检索白名单；无证据不生成支持结论 |
| GET /api/report | 仅包含已确认事实 |
| DELETE /api/documents/{id} | 级联清除事实和关联任务，再移除原件 |
| DELETE /api/account | 清除账户及关联数据；生产备份删除策略仍需实施 |
| POST /api/institution/simulations | name、inputs；确定性计算并保存输入输出 |

完整机器可读接口由运行中的 `/openapi.json` 提供。会话为 HttpOnly SameSite Cookie，写操作带 X-CSRF-Token；生产必须开启 Secure Cookie 和 HTTPS。

## OCR 选择与实际验证边界

当前按用户选择使用百度托管 PaddleOCR-VL 异步解析服务，使用已配置的百度 API Key / Secret Key 获取令牌，提交、轮询并下载结构化结果。校验结果下载域名、页数与页码，保留表格及来源；不使用百度通用文字识别接口。[官方接口文档](https://cloud.baidu.com/doc/OCR/s/Qmncwhwdt)

“效果最好”不能仅凭通用榜单断言。PaddleOCR-VL-1.6 的公开研究报告文档基准成绩，并不能证明在中文乳腺病理、检验单、手写医嘱上均优于其他服务。[研究论文](https://arxiv.org/abs/2606.03264)

上线前用经授权的脱敏样本建立对照集，覆盖文字 PDF、扫描 PDF、手机倾斜照片、低照度、表格、印章遮挡、病理指标和多页资料。比较 PaddleOCR、腾讯高精度通用识别及适用的医疗结构化接口；腾讯医疗 PDF 接口存在文档类型范围限制，不能假设覆盖全部病历。[腾讯医疗结构化计费与接口说明](https://cloud.tencent.com/document/product/1314/54264)

评测应统计关键字段完全正确率、数值和单位正确率、日期正确率、原文定位准确率、漏页率、人工核对时间、失败恢复率、P95耗时及每份成本。高风险字段错误须进入待核对；不得用“整体识别率”掩盖剂量、日期和指标错误。已完成虚构图片及扫描 PDF 的真实接口测试，但没有代表性样本跑分，不能宣称已选出最终最优 OCR。

## 境内服务与成本假设

模型采用 Kimi 开放平台 `kimi-k3`，境内接口 `https://api.moonshot.cn/v1`，已验证账户模型列表和实际调用。LangGraph 执行安全分流、检索、生成及引用校验；SQL 保存当前账户的对话历史，不向外部追踪平台发送内容。结构化输出只读取 content，不保存模型思考过程。[Kimi K3 文档](https://platform.kimi.com/docs/guide/kimi-k3-quickstart)

本地解析不调用外部服务；启用 OCR/模型后的真实请求按服务商计费。预算使用公式：月 OCR 页数 × 单页有效价格 + 输入/输出 token × 对应单价 + 计算、数据库、对象存储、备份及流量。具体采购价格、合同留存期与账单配额尚未确定，因此不编造固定报价。建议试点先限制账户、每文件40页、每账户200份资料，并设置服务商硬配额。

百度 PaddleOCR 凭证与 Kimi API Key 已存入被版本库忽略的服务端 `app/.env`；境内部署阶段还需要云账户、PostgreSQL 连接串、对象存储凭证、域名与 HTTPS 配置。都应由管理员填入服务端密钥管理，不通过患者界面填写。

## OCR离线评分工具

`audit/score_ocr.py` 读取人工标注 corpus 与各服务导出的 predictions，不联网、不上传患者资料。示例结构位于 `verification/ocr-corpus-template.json`。预测文件使用相同 id、text、page_count、critical_fields，可附 latency_seconds、cost 和 error。执行：

```powershell
.venv/Scripts/python.exe audit/score_ocr.py corpus.json provider-predictions.json --output report.json
```

为每个候选服务分别运行后对照报告。关键字段按单独结构化字段严格比对；遗漏样本计入失败，避免只统计成功请求。此工具不替代人工对照原件和正式样本设计。
